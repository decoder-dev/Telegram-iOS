## 2. C-1 (P1). Фильтры сообщений: матчинг без бюджета на UI-потоке

### Как устроено

`submodules/TelegramUIPreferences/Sources/ForkExtrasSettings.swift`:

- `maxPatterns = 64` (строка 1198), длина шаблона ≤ 512 UTF-16 (строка 1250), вход обрезается до
  `maxMatchUTF16Length = 4096` (строки 1191, 1292);
- компиляция — вне лока, с кэшем по «отпечатку» настроек (`apply`, строки 1225–1260);
- матчинг — `ForkRegexMessageFilters.matches(_:regexes:)`, строки 1277–1305:

```swift
let range = NSRange(location: 0, length: min(nsText.length, 4096))
for regex in expressions { if regex.firstMatch(in: text, options: [], range: range) != nil { return true } }
```

Никакого ограничения по времени, отмены или учёта стоимости.

### Где исполняется

- `submodules/ChatListUI/Sources/Node/ChatListItem.swift:109` — при отрисовке строки списка чатов
  (превью последнего сообщения);
- `submodules/TelegramUI/Sources/ChatHistoryEntriesForView.swift:190` — при построении истории чата
  (для каждого входящего сообщения, у которого есть кнопки — в том числе их подписи и ссылки).

Оба пути — UI-конвейер. Кэш (`ForkChatListMessageFilterCache`) спасает повторные вызовы, но не первый.

### Замер

Заглушка `banana-ios-audit-evidence/regex-freeze/` использует ровно те же границы и тот же вызов
`NSRegularExpression.firstMatch(in:options:range:)` (Swift 6.0.3, ICU из corelibs-foundation):

```text
(a*)*b  n=16   → match=false, 8 ms
(a*)*b  n=32   → (нет результата за 20 с, процесс снят)
(a*)*b  n=512  → (нет результата за 20 с)
(a*)*b  n=4096 → (нет результата за 20 с)
```

То есть сообщение из 33 символов (32 «a» и «!») при фильтре `(a*)*b` — это зависший главный
поток: сначала «приложение не отвечает», затем watchdog-kill. Обрезка входа до 4096 символов
проблему не решает: катастрофический бэктрекинг начинается с десятков символов.

### Почему это важно именно здесь

На Android-стороне того же проекта (BananaGram Android, rc.8) ровно этот класс дефекта уже
исправлен: `BoundedMatch` с бюджетом 20 мс на каждый матч и отбрасыванием «дорогого» выражения.
На iOS защита — только по длине. То есть форки разошлись в гарантиях, и iOS-версия отстала.

### Как исправлять

- Матчить в фоне: кэш вердиктов по (`stableVersion` сообщения, ревизия фильтров), вычисление —
  на отдельной очереди, UI читает готовое; для непосчитанного — «не скрывать» (fail-open).
- Дедлайн на матч (аналог `BoundedMatch`): проверять время внутри `CharacterView`/через
  `NSRegularExpression.enumerateMatches` с прерыванием по бюджету, «дорогое» правило временно
  отключать и показывать это в настройках.
- Не отдавать пользовательские регулярки в UI-путь вообще: считать «скрыто/не скрыто» при
  построении entries в фоне и складывать в кэш.

## 3. C-2 (P1). `tg://ayu/filters/import/…` ставит фильтры без подтверждения

`submodules/TelegramUI/Sources/OpenUrl.swift`:

- маршрут `ayu/filters/import/<host/path>` (строки 1045–1050);
- `handleAyuFiltersImportDeepLink` (строка 388) проверяет только хост из списка
  `dpaste.com`, `gist.githubusercontent.com`, `pastebin.com`, `nekobin.com` (строки 381–386),
  затем `URLSession` тянет plaintext и строки файла дописываются в
  `regexMessageFilterPatterns`, причём `regexMessageFiltersEnabled = true` (строка 427).

### Что это значит на практике

Никакого диалога подтверждения нет. Пользователь тапает ссылку — фильтры уже применены;
максимум, что он увидит, — открытый экран настроек фильтров уже после факта.

Содержимое контролирует отправитель ссылки. Достаточно создать пасту на любом из четырёх
сайтов: `tg://ayu/filters/import/pastebin.com/raw/XXXX`. Список хостов ничего не даёт — он
ограничивает не автора контента, а лишь площадку хранения.

### Следствия

- `^.*$` — скрыть все входящие сообщения во всех чатах (включая служебные предупреждения);
- `(a*)*b` — фриз приложения (C-1) при первом же подходящем сообщении;
- `merged.suffix(64)` — вытеснение собственных фильтров пользователя;
- фильтр `<type>N</type>` — выборочное скрытие, например, всех фото или всех документов.

Фетч не ограничен ни по размеру ответа, ни по таймауту (дефолт `URLSession`), и результат
попадает в настройки, минуя какой-либо канал проверки.

### Как исправлять

- Показывать подтверждение со списком шаблонов, которые будут добавлены (это дешево — данные уже
  в памяти), и не включать фильтрацию автоматически.
- Ограничить размер ответа (например, 64 КБ) и число строк; таймаут 10 с.
- Не позволять импорту менять `regexMessageFiltersEnabled` — только добавлять шаблоны в список.

## 4. C-3 (P2). Ключи авторизации в Keychain открытым JSON

`submodules/TelegramUIPreferences/Sources/SessionKeychainBackup.swift`:

- `save` пишет `JSONEncoder().encode(AccountBackupData)` — это auth-ключи аккаунта и параметры
  датацентров — в generic-password item;
- класс защиты `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (строка 21): читается при
  заблокированном экране после первой разблокировки, то есть в фоне, из бэкапа с паролем и любым
  процессом, получившим доступ к keychain устройства;
- шифрования поверх Keychain нет: PBKDF2/биометрия не используются (в отличие от пароля Архива);
- `loadAll()` (строка 43) читает все аккаунты сразу;
- item'ы переживают удаление приложения; чистятся только по `delete`/`deleteAll` при выходе из
  аккаунта (`SharedAccountContext.swift:870`, `:1426`).

Смысл функции понятен: переустановка тем же сертификатом (E-Sign) не теряет сессию, потому что
Keychain переживает удаление приложения. Но цена — второй экземпляр самых чувствительных данных
приложения в контейнере с более слабым классом защиты, чем `WhenUnlockedThisDeviceOnly`, который
используется для пароля Архива (`ArchivePasswordKeychain.swift:20`).

**Как исправлять:** либо `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` + `SecAccessControl` с
`.userPresence` (Face ID) на чтение, либо шифровать blob ключом, производным от пароля Архива /
Keychain-ключа с `WhenUnlocked`, либо (проще) хранить только «указатель» и требовать повторного
входа.

## 5. C-4 (P2). Пароль Архива: две копии, одна из них перезаписывает Keychain

- `ArchiveLockHelpers.swift:29-46` — при каждом открытии Архива, если в Postbox-настройках
  (`chatArchiveSettings.passwordVerifier`) пусто, туда кладётся копия Keychain-хэша;
- `ArchivePasswordKeychain.swift:88-110` — `matchesPassword` принимает совпадение с любой из двух
  копий, и при совпадении с резервной делает `storeHash(backup, …)`, то есть перезаписывает
  Keychain значением из настроек.

Следствие: защищённость Архива понижается с «секрет в Keychain» до «секрет в Keychain или в базе
настроек аккаунта», которую пишет приложение и которая лежит в App Group-контейнере. Для локального
атакующего с доступом к файлам контейнера (джейлбрейк, отладочная сборка, восстановление из бэкапа)
это обход всей Keychain-защиты: он подставляет свой verifier в настройки, и первый же ввод пароля
перепишет Keychain. Комментарий в коде признаёт риск для старого SHA-256 (`backupIsWeak`), но
PBKDF2-копия остаётся в настройках навсегда.

**Как исправлять:** держать в настройках только «наличие пароля» (булев флаг) и, при необходимости,
«поколение»; резервную копию использовать только для одноразового восстановления с явным
подтверждением пользователя («восстановить пароль из копии настроек?»), а не как молчаливый
альтернативный источник истины.

## 6. C-5…C-8. Прочее по приватности, транспорту и релизу

### C-5 (P2). `allowInsecure` в VLESS-ссылке

`VlessProfile.swift:296-310` принимает `allowInsecure=1|true` из share-ссылки, `VlessXrayConfig`
кладёт это в TLS/REALITY-настройки (`"allowInsecure": profile.allowInsecure`). Для пользователя это
невидимо: ссылку прислали — туннель пошёл без проверки сертификата, и оператор туннеля (или MITM)
читает весь трафик. Ирония в том, что это ровно тот сценарий, ради защиты от которого люди ставят
VLESS. Минимум — предупреждение в редакторе профиля и бейдж «без проверки TLS» в списке прокси;
лучше — не принимать флаг из ссылок вовсе, оставив его только ручной настройкой.

### C-6 (P2). Два источника истины у призрачных флагов

`ForkGhostModeSettings` (UserDefaults-зеркало, `ManagedLocalInputActivities.swift:510-575`) и
`ForkExtrasSettings.ghostDontReadMessages` (Codable в настройках аккаунта,
`ForkExtrasSettings.swift:1034-1054`) описывают одно и то же. Мотив зеркала понятен (холодный старт
не должен успеть отправить «онлайн»/прочтение), но синхронность нигде не проверяется: нет ни теста,
ни assert'а на совпадение, а пишутся они из разных мест (`SharedAccountContext.swift:1309` —
в `ForkRegexMessageFilters.apply`, отдельный путь — `applyPreferences`). Любая правка одной ветки
даёт состояние «в интерфейсе призрак, в протоколе — нет» (то есть утечку) или наоборот.

### C-7 (P2). Глобальное окно «читать при взаимодействии»

`beginReadOnInteractOverride()` (`ManagedLocalInputActivities.swift:606-631`) ставит глобальный
`interactOverrideActive = true` на 1,5 с; всё, что проверяет флаг, в это окно пропускает чтения и
показывает «онлайн» — в любом чате и в любом аккаунте. Поколение (`generation`) корректно
защищает от «залипшего» флага, но не от чужих чтений: достаточно, чтобы в это окно прилетел
синхронизационный read другого чата/аккаунта. Это та же ошибка, что была в Android-версии
(B-5: общий флаг разрешения на чтение), и лечится так же — per-chat/per-account разрешением.

### C-8 (P2). Релизный процесс

`.github/workflows/build.yml`:

- триггеры `push: tags: ['v*']` и `workflow_dispatch` (строки 19–24) — релиз публикуется по любому
  тегу, то есть по произвольному коммиту, включая не-main;
- `permissions: contents: write` на уровне workflow (строки 51–52); задача `build` собирает
  бинарник из сторонних сабмодулей (`git submodule update --init --recursive`, патч `tgcalls`,
  скачивание `libxray`) и в ней же выполняется `gh release create` — то есть код из сабмодулей
  исполняется в контексте, у которого есть право писать в релизы;
- `actions/checkout@v5` и т.п. — по тегу, а не по SHA (в `security-regressions.yml`, наоборот, по
  SHA: практики расходятся);
- `skip_regression` (строки 34–38) позволяет собрать и опубликовать IPA без единого теста;
- защиты от подмены артефакта нет: в релиз кладётся только IPA, `sha256` берётся из API, отдельного
  `SHA256SUMS`/`build-info.txt` (как в Android-репозитории) нет.

Что сделано хорошо: скачивание `libxray` проверяется по sha256 (строки 214–216), сабмодули
зафиксированы gitlink'ами, regression-задача имеет `contents: read`.

## 7. Мелкие наблюдения (P3)

### C-9. Якоря `^`/`$` в фильтрах ломаются на границе обрезки

Поскольку `matches` ищет в окне `0..<4096`, ICU считает концом строки конец окна: `(a+)+$` на
строке «…4096 a…!» возвращает `true` (замер в `results/regex-freeze-linux.txt`), хотя для полного
текста это `false`. Любой фильтр вида `\d$`, `.*$`, `.{4096}$` будет вести себя непредсказуемо на
длинных сообщениях, а фильтры по «хвостовому» `<type>N</type>` (они специально дописываются в
конец) перестанут работать на длинных текстах. Правильно — матчить по полному тексту в фоне
(см. C-1) либо явно документировать семантику окна.

### C-10. `BananaMediaURLPolicy` без защиты от DNS-rebinding

`BananaMediaURLPolicy` (`BananaLinkDownloader`) — крепкая (только https, порт 443, без учётных
данных в URL, отказ от IP-подобных хостов и локальных суффиксов), но имя публичного вида может
резолвиться в `127.0.0.1` (DNS-rebinding) — адреса проверяются по имени, а не по разрешённому IP
на этапе соединения. Для SSRF-класса это остаточный риск; лечится проверкой
`URLSessionTaskMetrics.remoteAddress` или пиннингом IP.

### C-11. App Store-конфигурация в sideload-сборке

`build-system/sideload-configuration.json`: `is_appstore_build: "true"` и `appstore_id: "686449807"`
(идентификатор официального Telegram) вместе с поддельным bundle id `ph.teleg.Telegrapf` и
`team_id C67CF9S4VU`. В такой сборке работают App-Store-ветки кода (внутренние покупки, часть
премиум-путей), хотя подпись чужая и IAP невозможен; плюс в репозитории лежат `api_id`/`api_hash`
официального приложения — все сборки форка идут под ними.

### C-12. VLESS-разбор: sockopt без валидации

VLESS-разбор: sockopt-значения из ссылки не валидируются по диапазону (`VlessProfile.swift:418-425`:
`Int(rawDownFrame)` без границ), path/sni не ограничены по набору символов (защита есть только от
пробела и `\0`), `decodeXhttpExtra` проверяет размер после парсинга. JSON собирается через
`JSONSerialization` (это хорошо — инъекции в конфиг нет), но «мусорные» значения доходят до ядра
Xray.

### C-13. Пробелы в тестах

В `Tests/` есть 49 проверок, включая тонкие (`GhostMode`, `ArchiveLock/*`, `ManagedProxy`,
`NetworkPolicies`, `NetworkRecovery`), но ни одной на фильтры сообщений и на импорт фильтров по
ссылке — при том что именно там найдены C-1, C-2 и C-9.

## 8. Что сделано хорошо

Это не формальность — перечисленное проверено и работает:

- **Fail-closed у транспорта.** Пока VLESS/WEB-профиль не поднялся, MTProto не «падает в директ»,
  а получает заведомо закрытый локальный маршрут (`ProxySettings.swift:266-291`, комментарий
  «An unresolved managed profile must block every MTContext consumer»), плюс бэкофф 1→60 с и сброс
  попыток после успешного старта (`VlessManager.swift:190-215`). Для приватного форка это главное.
- **Парсинг VLESS** — строгий allowlist параметров, отказ вместо «молча проигнорировать», проверка
  длины URI (8192), валидация REALITY-ключа (base64url/32 байта), запрет лишних параметров для
  каждого транспорта (`VlessProfile.swift`).
- **Пароль Архива:** PBKDF2-HMAC-SHA256, 100 000 итераций, случайная соль,
  `WhenUnlockedThisDeviceOnly`, прозрачный апгрейд старых SHA-256-хэшей, throttling в Keychain с
  `CLOCK_MONOTONIC` (перевод часов не сбрасывает cooldown), константное сравнение хэшей.
- **Глубина защиты Архива:** редактирование уведомлений и CallKit, удаление доставленных
  уведомлений по peerId, удаление Siri-интентов, скрытие в поиске/шэринге/виджетах/Spotlight,
  отключение медиа-оверлея, перекрытие окна при уходе в фон (`ArchiveLockHelpers.swift`).
- **Чистка трекинг-параметров ссылок** (`ForkTrackingURL/Links.swift`) — с отказом от изменения
  подписанных ссылок (`signature`, `x-amz-*`, `x-goog-*`), проверкой control-символов и своим
  тестом (`Tests/ForkRefinements`).
- **On-device AI** (`ForkOnDeviceAI.swift`) — только Apple Foundation Models, «ничего не покидает
  телефон», слабая линковка и graceful «недоступно».
- **Телеметрия** (`ForkPerformanceTelemetry.swift`) — только локальные логи, ни одного сетевого
  вызова: проверено grep'ом по файлу (нет `URLSession`/`URLRequest`).
- **Лог-экспорт** (`ForkLogExport.swift`) — потоковая упаковка без чтения всего архива в память,
  hardlink + zip с диска, работа вне главного потока.
- **Локальные «теневые» функции** (`TelegramShadowBan`, `BananaSpyStorage`, `BananaBannedChats`) —
  данные не покидают устройство, хранятся в Postbox-кэше или `TelegramSimpleSettings`.
- **Гигиена релиза iOS-репозитория** лучше, чем у Android-соседа: тег совпадает с проверенным
  коммитом, CI на нём зелёный, sabotage-риска «в main уехало после тега» нет.

## 9. Как проверялось и чего проверить не удалось

### Проверено

- чтение кода: `submodules/TelegramCore/Sources/Arena/*`, `Fork*`, `Banana*`,
  `WebProxyTransport/*`, `TelegramVLESS/*`, `BananaLinkDownloader/*`, `ArchiveLockHelpers`,
  `ArchivePasswordKeychain`, `SessionKeychainBackup`, `ManagedLocalInputActivities`,
  `ProxySettings`, `ChatListUI`/`TelegramUI` точки применения фильтров, `NotificationService`,
  все 8 workflow-файлов;
- прогон собственных проверок форка на Linux: 33 из 49 — PASS
  (`results/fork-ci-checks-linux.txt`). Остальные 16 падают только из-за macOS-only API и
  инструментов (`os_unfair_lock`, `CoreGraphics`, `Darwin`, `NSDataDetector`, `swift test` с
  зависимостями, `cmake`/`ffmpeg` для CodeScanning), а не из-за кода форка — проверено на примерах
  (`ClientAdditions` → `no such module 'CoreGraphics'`, `NetworkRecovery` → `no such module 'Darwin'`);
- замер стоимости матчинга регулярок на реальном `NSRegularExpression` (Swift 6.0.3 + ICU,
  `regex-freeze/`): воспроизведён фриз на 33 символах и «ложное срабатывание» якоря `$` на
  границе окна;
- сверка с upstream по спорным местам: `NSAllowsArbitraryLoads` в `Info.plist` и `ali-fareed/*`-форки
  в `.gitmodules` — это upstream, а не регрессия форка (проверено по
  `raw.githubusercontent.com/.../master`), поэтому в находки не включено;
- `git log -L` по подозрительным логам в `NotificationService` — они upstream 2021–2023 годов,
  тоже не включены;
- состояние CI/релизов через GitHub API.

### Не проверялось (и в этой среде невозможно)

- сборка приложения: нет macOS, Xcode, iOS SDK, Bazel-тулчейна; Linux-Swift 6.0.3 не собирает
  проект (Apple-only API). Соответственно не проверены: компиляция, работа на устройстве,
  реальный UI, утечки памяти, поведение под watchdog, VoIP, платежи, Passport, media pipeline;
- запуск UI-тестов и `swift test`-пакетов, требующих UIKit/CoreGraphics;
- сетевые сценарии с реальным VLESS/MTProto-сервером, Web-прокси и libxray (бинарник только в CI);
- jailbreak/forensics-сценарии для C-3/C-4 (оценка по коду и модели угроз, не по эксперименту);
- сравнение с upstream «строка в строку» по всем 2 800 изменённым файлам — выборочно, по
  риск-ориентированному списку.

## 10. Приоритетный план

1. **C-1 + C-9** — вынести матчинг фильтров в фон с дедлайном, кэшировать вердикты, матчить по
   полному тексту (или явно ограничить семантику). Это единственный дефект, который пользователь
   ловит «в один тап».
2. **C-2** — подтверждение перед импортом, лимиты ответа/таймаут, не включать фильтрацию
   автоматически.
3. **C-3** — сузить класс защиты Keychain-копии сессии (или шифровать её ключом Архива/биометрией).
4. **C-4** — не перезаписывать Keychain из настроек молча; хранить в настройках только флаг.
5. **C-7/C-6** — per-chat/per-account разрешение на «прочитать при взаимодействии»; один источник
   истины для призрачных флагов + тест на совпадение.
6. **C-5** — предупреждение (или запрет) для `allowInsecure` из ссылок.
7. **C-8** — `contents: read` у сборочной задачи, `contents: write` только у отдельной
   publish-задачи; запретить публикацию с тегов не на main; убрать `skip_regression` из релизного
   пути; добавить `SHA256SUMS` в релиз; запинить actions по SHA.
8. **C-13** — тесты: (а) бюджет матчинга/отсутствие фриза, (б) импорт по ссылке требует
   подтверждения и не включает фильтры, (в) якоря на длинных текстах.
