## F01 — P1: отправка из камеры потеряла параметры отправки

Файл: `submodules/TelegramUI/Sources/ChatControllerOpenAttachmentMenu.swift:2027`.
В `openCamera` completion вызывает `enqueueMediaMessages(... silentPosting: false, scheduleTime: nil ...)`. В исходном официальном пути `legacyCamera` есть `presentSchedulePicker` и передача выбранных параметров. Новая цепочка `CameraScreen` их не предоставляет; это прямо отмечено комментарием temporary gap.

Сценарий проверки: обычный чат → скрепка → камера → снимок → выбрать отправку без звука/по времени. Должны быть доступны соответствующие действия и переданы выбранные значения. Этот вывод относится к камере; обычная галерея имеет отдельный путь с параметрами. Не утверждается, что все способы планирования сообщений сломаны.

## F02 — P2: из того же пути камеры исчез выбор таймера медиа

Файл: `submodules/TelegramUI/Sources/ChatControllerOpenAttachmentMenu.swift:2009`.
Оригинальный `openCamera` передавал `presentTimerPicker`; новая цепочка его не подключает, completion не принимает таймер. Проверить на личном чате, где оригинал предлагает таймер для снятого медиа. Нужно восстановить действие и передачу срока в сообщение; не только кнопку.

## F03 — P2: распознавание QR-прокси из камеры чата не перенесено

Файл: `submodules/TelegramUI/Sources/ChatControllerOpenAttachmentMenu.swift:1994`.
Оригинальный `recognizedQRCode` разбирал `parseProxyUrl` и вызывал `openResolved(.proxy(...))`. При замене старой камеры этот callback удалён, а в новой цепочке `openCamera` эквивалента нет. Это регрессия конкретного входа через камеру чата, а не утверждение, что в приложении вообще нет QR-сканера.

## F04 — P1: импорт истории может сообщить успех после потери вложений

Файл: `submodules/TelegramUIPreferences/Sources/MessageSavingStore.swift:673–699`.
Сначала `importJSONData` меняет записи. При replace затем удаляются существующие вложения; новые копируются через `try?`. Ошибки копирования не меняют возвращаемый `.success`. При недоступном исходном файле/ошибке записи пользователь получает успешный импорт, хотя старый файл удалён, а новый не сохранён.

Нужны staging-каталог, проверка всех копий до замены, атомарный переход и сообщение об ошибке. Тест: отказ копирования после первой успешной копии, без потери прежней базы и вложений. Намеренный импорт JSON без вложений следует отличать от ошибки копирования.

## F05 — P1: экспорт истории может создать неполную резервную копию без ошибки

Файл: `submodules/TelegramUIPreferences/Sources/MessageSavingStore.swift:637–645`.
Ошибки чтения папки, создания папки вложений и copyItem подавлены; экспорт возвращает URL как успешный, если записан JSON. При сбое копирования медиа резервная копия выглядит полноценной. Требуется отказ с понятной ошибкой или явное подтверждение неполной копии со списком отсутствующих файлов.

## F06 — P2: loading/error истории существуют только как недостижимые варианты

Файл: `submodules/SettingsUI/Sources/MessageSavingHistoryController.swift:26,120`.
Enum содержит loading/error, но генератор выдаёт только empty/record, а сигнал не публикует loading и не передаёт ошибки хранилища. Пока снимок загружается, обещанный статус не показывается; ошибки не становятся состоянием error. Нужно соединить результат чтения и состояния UI, локализовать текст.

## F07 — P2: повторный запрос пароля архива теряет completion

Файл: `submodules/ChatListUI/Sources/ArchiveLockHelpers.swift:533`.
Если диалог того же аккаунта открыт, функция выходит без onSuccess/onCancel. Второй вызывающий путь, ожидающий completion разблокировки, никогда не получает результат. Нужна очередь ожидающих или явно завершённая отмена второго запроса. Не ослаблять проверку authorizationGeneration и не открывать архив по одному лишь наличию диалога.
